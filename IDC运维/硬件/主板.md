
## 主板故障

### 更换主板的SOP

#### 适用范围与前提

本 SOP 适用于 IDC 运维中**因主板硬件故障而更换服务器主板**的场景，前提是**复用原硬盘、网卡、RAID 卡等插卡**，以避免操作系统和业务数据重装。若整机替换或硬盘同时更换，则不属于本文范围。

更换主板并非简单的硬件替换。新主板的 BMC 与 BIOS 配置会恢复出厂默认，板载网卡的 MAC 地址会变更，Linux 侧的网卡命名和绑定配置也可能随之失效。SOP 的核心，是在动手之前把**可恢复的状态**完整留存，在换完之后按顺序**重建**。

---

#### 第一阶段：更换前——必须完成的记录与备份

这一阶段的每一项记录，都是更换后恢复的依据。遗漏任何一项，都可能导致更换后需要登录机房现场或重装系统。

**BMC / 带外管理配置**：登录 BMC Web 界面（iDRAC、iLO、iBMC 等），记录 **BMC IP 地址、子网掩码、默认网关、用户名**，以及 **License/Key**（如 iLO Advanced、iDRAC Enterprise）。若支持配置导出，直接导出 BMC 配置文件。

**SEL 与 FRU**：通过 `ipmitool` 导出系统事件日志和 FRU 信息。SEL 是硬件故障的历史证据，在保修索赔中可能被要求提供；FRU 记录了原主板的 **SN 和型号**，是更换后烧录或核对资产信息的基础。

```bash
ipmitool -I lanplus -H <BMC_IP> -U <用户> -f <密码文件> sel elist > sel-backup-$(date +%F).txt
ipmitool -I lanplus -H <BMC_IP> -U <用户> -f <密码文件> fru > fru-backup-$(date +%F).txt


-I Interface
-H HostName
-U User
```

**BIOS / UEFI 配置**：记录启动模式（UEFI/Legacy）、启动顺序、CPU/内存相关设置、SR-IOV 或 VT-d 等虚拟化选项。Lenovo 服务器可用 XClarity Essentials OneCLI 将系统配置保存到外部介质；Dell 的 Easy Restore 会在更换后自动提示恢复备份的 UEFI 配置。

**线缆清单与物理位置**：拔下每根线缆时**逐一记录**其连接位置（端口号、槽位号）。硬盘、网卡、HBA 卡必须**按原槽位**插入新主板或机箱，否则 Linux 网卡命名和 RAID 配置可能错位。

**固件版本基线**：记录当前 BIOS、BMC 及 CPLD 固件版本。更换主板后，新主板固件版本可能与旧板不同，需要**统一到与原环境一致的版本**，或统一升级到经过验证的最新版本，避免因固件差异引入兼容性问题。

---

#### 第二阶段：下电与硬件拆卸

**下电操作**：通过 BMC 或操作系统正常关闭主机，而非直接拔电。确认业务已迁移或停止，电源状态为 off 后再进行下一步。

**防静电**：佩戴**防静电腕带**并良好接地，去除手表、戒指等导电物体。拆下的 DIMM、CPU、PCIe 卡必须放置在**防静电台面或防静电袋**中，不可直接放在机箱外壳或普通桌面上。

**拆卸顺序（典型，以具体机型手册为准）**：断开所有外部线缆（光纤、以太网、电源）→ 卸下顶盖 → 拆除导风罩、风扇架、PCIe Riser → 拔下主板上所有内部线缆并**对照线缆清单确认无遗漏** → 依次卸下 DIMM、CPU 及散热器（注意 CPU 插槽针脚保护）、RAID 卡/网卡等插卡 → 卸下固定主板的螺丝，取出旧主板。

**CPU 与插槽保护**：拆下 CPU 时严禁触碰插槽针脚；旧主板退回前，需将新主板附带的 **CPU 插槽保护盖**安装到旧主板上，防止运输中损坏针脚。

---

#### 第三阶段：新主板安装与最小化验证

**复装复用部件**：将原 DIMM **按原槽位**插入新主板，安装 CPU 和散热器，按**线缆清单**逐根接回内部线缆，插入 PCIe 卡和 LOM 网卡。所有复用部件保持与原槽位一致。

**最小化上电验证（不接业务网络）**：先不接入业务网线，仅连接 BMC 管理口和电源，通过 BMC 远程开机。观察是否有硬件告警（POST 错误、风扇异常、内存/CPU 报错）。在确认硬件层面无异常之前，不进行 BMC 配置修改或业务网络接入，避免将硬件问题误判为配置问题。

---

#### 第四阶段：更换后配置恢复

**BMC 网络与访问恢复**：新主板 BMC 默认可能为 DHCP 或固定 IP。通过 BMC 的默认地址或本地 Console 进入，将 **BMC IP、掩码、网关**设置为与原环境一致，恢复用户账号和 **License/Key**。若更换前导出了 BMC 配置文件，优先导入；但注意导出的配置可能**不包含密码**，用户密码需要手工重设。

**SN / 服务编号**：新主板的 SN 是空白的或为新 SN，必须恢复为原 SN，否则资产系统、保修记录和监控平台会出现标识错乱。

- **Dell**：开机时 BIOS 检测到新主板和备份闪存中的旧 Service Tag，会提示 **Easy Restore**，按 `Y` 可自动恢复 Service Tag、iDRAC License 和 UEFI 配置。若 Easy Restore 不可用，进入 **System Setup → Service Tag Settings** 手工录入。
- **华为**：需使用 SmartKit 等工具将原 SN **烧录**到新主板，否则 iBMC 中 SN 显示为空。
- **其他品牌**：参照对应厂商的维护手册执行 SN 写入或恢复。

**BIOS / RAID 配置**：按更换前记录的基线恢复启动模式、启动顺序和虚拟化选项。若服务器使用硬件 RAID 卡，更换主板后 RAID 配置可能丢失，需要在 RAID 卡管理界面中**导入外部配置（Import Foreign Configuration）** ，或确认 UEFI 启动模式下是否已自动导入。

---

#### 第五阶段：操作系统内网络配置修复（关键易漏环节）

主板更换后，**板载 LOM 网卡的 MAC 地址会发生变化**。Linux 的 `udev` 和网络脚本仍绑定着旧 MAC，会导致网卡名称漂移或接口无法启动。

**清理 udev 持久化网络规则**：进入 `/etc/udev/rules.d/`，备份后删除 `50-persistent-net.rules` 或 `70-persistent-net.rules`。系统重启后会基于新 MAC 重新生成规则。

```bash
cd /etc/udev/rules.d
cp 70-persistent-net.rules 70-persistent-net.rules.bak-$(date +%F)
rm -f 50-persistent-net.rules 70-persistent-net.rules
```

**更新或注释 ifcfg 文件中的 MAC 绑定**：进入 `/etc/sysconfig/network-scripts/`，检查 `ifcfg-*` 文件中的 `HWADDR=` 或 `MACADDR=` 行。如果该值与新网卡的实际 MAC 不一致，网卡会拒绝启动。可将旧 MAC 行**注释掉**（行首加 `#`），或将其更新为 `ip a` / `ifconfig` 显示的新 MAC。

**Bonding 场景额外注意**：如果使用了 bond，除物理网卡配置外，还需检查 `ifcfg-bondX` 中的 `MACADDR` 行，同样注释或更新。部分平台（如 FusionCompute）的管理网口也可能绑定了 MAC，需一并处理。

**刷新规则并重启验证**：执行 `udevadm control --reload-rules && udevadm trigger --subsystem-match=net`，然后重启主机，确认网卡名称、IP、bond 状态与更换前一致。

---

#### 第六阶段：验证与收尾

**硬件层**：BMC 中无新增严重告警；`ipmitool sensor` 各传感器状态为 `ok`；`ipmitool sel elist` 中无与本次更换相关的未处理错误；FRU 中的 **SN 已恢复为原值**。

**带外管理层**：BMC IP 可达，Web 登录正常，用户权限和 License 状态正常；`ipmitool chassis power status` 可控。

**系统与网络层**：操作系统正常启动；`ip a` / `ip link` 显示网卡名称与更换前一致；业务 IP 可达，bond 状态正常（如 `cat /proc/net/bonding/bondX`）；关键服务进程已启动。

**业务层**：按业务清单逐项验证端口监听、应用健康检查和依赖调用。确认无误后，恢复监控告警，更新资产台账中的**主板 SN、BMC MAC（若变更）** 及维修记录，归档本次更换的 SEL、FRU 和配置备份文件。

---

#### 检查清单（速查）

| 阶段       | 必做项                                                                       |
| -------- | ------------------------------------------------------------------------- |
| 更换前      | 记录 BMC IP/网关/账号/License；导出 SEL、FRU；记录 BIOS 配置；列线缆清单；记录固件版本                |
| 拆卸       | 防静电；按清单逐一标记线缆；CPU 插槽保护；DIMM/插卡防静电存放                                       |
| 安装       | 复用部件**原槽位**；按线缆清单复接；最小化上电验证硬件                                             |
| 配置恢复     | BMC IP/账号/License 恢复；**SN 烧录或 Easy Restore**；BIOS/RAID 配置导入               |
| Linux 网络 | 删除 `*-persistent-net.rules`；注释/更新 `ifcfg` 中的 `HWADDR/MACADDR`；刷新 udev 后重启 |
| 验证       | 硬件无告警、SN 正确、网络与 bond 正常、业务逐项确认                                            |

## BMC

### 主要功能

- **远程开关机、重启、强制下电**；
    
- **KVM over IP**：远程看服务器屏幕、模拟键盘鼠标；
    
- **远程挂载虚拟光驱/ISO**，用于装系统；
    
- **硬件监控**：温度、风扇、电压、电源、硬盘/内存等传感器状态；
    
- **告警和日志**：硬件故障日志、系统事件日志；
    
- **BIOS/UEFI 配置**：部分服务器可通过 BMC 进入 BIOS 设置；
    
- **SOL/串口重定向**：远程查看串口输出；
    
- **用户权限和审计**：管理 BMC 登录账号。

### IPMItool

#### 远程连接通用格式

远程操作 BMC/iDRAC/iLO 时，基础命令结构如下：

```bash
ipmitool -I lanplus -H <BMC_IP> -U <用户名> -P <密码> <子命令>
```

- **`-I lanplus`**：使用 IPMI v2.0 加密接口，远程操作应优先使用，而非旧的 `lan` 接口。
- **本地执行**（在服务器操作系统内）可省略 `-H/-U/-P`，直接 `sudo ipmitool <子命令>`。
- 密码不便明文传递时，可用 **`-E`** 从环境变量读取，或 **`-f <密码文件>`**。
- 部分厂商（如 HP）BMC 的 LAN 通道号可能为 **2**，其他多数为 **1**，`lan`/`user` 类命令需注意通道号差异。


#### 电源与机箱控制

| 命令 | 作用 |
|---|---|
| `ipmitool chassis power status` | 查询当前电源状态（on/off） |
| `ipmitool chassis power on` | 开机 |
| `ipmitool chassis power off` | **强制下电**（直接切断供电，非正常关机） |
| `ipmitool chassis power cycle` | **冷重启**（先下电再上电） |
| `ipmitool chassis power reset` | **热重启**（类似按 Reset 键） |
| `ipmitool chassis power soft` | 发送 ACPI 软关机信号，请求 OS 正常关闭 |
| `ipmitool chassis status` | 机箱整体状态（电源、过载、故障、前面板锁定等） |
| `ipmitool chassis identify` | 点亮/关闭前面板定位灯（默认闪烁 15 秒） |
| `ipmitool chassis restart_cause` | 查询**上一次重启的原因** |

`chassis power off` 和 `power cycle` 会直接切断主机供电，可能造成数据丢失或文件系统损坏，须在变更窗口内执行。


#### 传感器与硬件健康

| 命令 | 作用 |
|---|---|
| `ipmitool sensor` 或 `ipmitool sensor list` | 读取**所有传感器**的当前读数与阈值状态（温度、电压、风扇转速等） |
| `ipmitool sdr` 或 `ipmitool sdr list` | 输出传感器数据记录（SDR），包含传感器名称、读数、状态 |
| `ipmitool sdr get <传感器名称>` | 查看指定传感器的详细 SDR 信息 |

`ipmitool sensor` 输出中**状态列**出现 `ok` 以外的值（如 `cr` 临界、`nc` 不可恢复）时，需立即关注对应硬件。


#### SEL 系统事件日志

| 命令 | 作用 |
|---|---|
| `ipmitool sel list` | 列出 SEL 原始记录 |
| `ipmitool sel elist` | **推荐使用**，以“传感器名称 + 状态”的可读格式输出，比 `list` 更直观 |
| `ipmitool sel clear` | **清空 SEL**（执行前务必先导出备份） |
| `ipmitool sel save <文件名>` | 将 SEL 导出到文件，便于归档或厂商报修 |


#### FRU 资产信息

FRU（Field Replaceable Unit，现场可更换单元）命令用于读取硬件出厂信息，是资产盘点和保修报修时获取 **SN、型号** 的核心手段。

| 命令 | 作用 |
|---|---|
| `ipmitool fru` 或 `ipmitool fru print` | 读取所有 FRU 的清单信息，包括**序列号（SN）、产品型号、资产标签、制造商**等 |
| `ipmitool fru print <FRU_ID>` | 仅查看指定 FRU（如主板、机箱、电源）的信息，常见 ID 为 `0` 或 `1` |


#### BMC 网络配置（LAN）

| 命令 | 作用 |
|---|---|
| `ipmitool lan print <通道号>` | 查看指定 LAN 通道的 BMC 网络配置，多数为**通道 1**，HP 常为**通道 2** |
| `ipmitool lan set <通道号> ipsrc static` | 将 BMC 地址获取方式设为**静态**（也可设为 `dhcp`） |
| `ipmitool lan set <通道号> ipaddr <IP>` | 设置 BMC 的 IP 地址 |
| `ipmitool lan set <通道号> netmask <掩码>` | 设置子网掩码 |
| `ipmitool lan set <通道号> defgw ipaddr <网关>` | 设置默认网关 |

修改 BMC 网络配置需谨慎，建议在带内或本地 Console 环境下进行，避免配置错误后带外彻底失联。


#### 用户与权限管理

| 命令 | 作用 |
|---|---|
| `ipmitool user list <通道号>` | 列出 IPMI 用户及其权限级别，常用 `1` |
| `ipmitool user set name <用户ID> <用户名>` | 设置或修改用户 ID 对应的用户名 |
| `ipmitool user set password <用户ID> <新密码>` | 修改指定用户的密码 |
| `ipmitool user enable <用户ID>` / `disable <用户ID>` | 启用或禁用某个用户账号 |


#### Serial-over-LAN（SOL）远程控制台

SOL 允许通过 IPMI 网络远程访问服务器的串口控制台，在 OS 网络不通或需要查看 BIOS/启动阶段输出时非常有用。

| 命令 | 作用 |
|---|---|
| `ipmitool sol activate` | 激活 SOL 会话，进入远程串口控制台 |
| `ipmitool sol deactivate` | 终止当前 SOL 会话 |
| `ipmitool sol info` | 查看 SOL 配置参数（波特率、启用状态等） |

退出 SOL 交互会话的快捷键通常是 **`~.`**（波浪号 + 句点），具体取决于终端软件配置。


#### 启动设备与引导控制

`chassis bootdev` 设置的是一次性引导覆盖，**仅在下次重启时生效一次**，之后恢复 BIOS 中配置的原有引导顺序。

| 命令 | 作用 |
|---|---|
| `ipmitool chassis bootdev pxe` | 设置**下次启动**从 PXE 网络引导 |
| `ipmitool chassis bootdev pxe options=efiboot` | UEFI 环境下设置 PXE 引导时，需附加 `options=efiboot` |
| `ipmitool chassis bootdev disk` / `cdrom` / `bios` | 将下次引导目标设为硬盘、光驱或 BIOS 设置界面 |


#### 管理控制器（MC）自身操作

| 命令 | 作用 |
|---|---|
| `ipmitool mc info` | 查看 BMC 控制器自身信息（**固件版本**、制造商、IPMI 版本等） |
| `ipmitool mc reset cold` / `warm` | **重启 BMC 控制器**（cold 为彻底重启，warm 为热重启） |
| `ipmitool chassis selftest` | 执行 BMC 自检并输出结果 |
| `ipmitool mc getsysinfo` | 读取系统信息（部分平台支持，可获取 BIOS/BMC 版本等） |


#### 原始命令与厂商扩展

`raw` 直接发送 IPMI 字节流，用于执行标准命令未覆盖的厂商私有功能，写错参数可能触发未定义行为，仅在有明确厂商文档或脚本依据时使用。

```bash
ipmitool -I lanplus -H <IP> -U <用户> -P <密码> raw <netfn> <cmd> [data]
```

日常运维中，`raw` 常用于厂商特定的 SEL 配置、用户权限精细控制、VLAN 设置等场景，具体字节序列需参考对应 BMC 厂商的接口文档。

## Bios

**Basic Input/Output System，中文叫“基本输入输出系统”**。它是固化在服务器/电脑主板上的**底层固件**，负责设备加电后最先运行的一小段程序：初始化 CPU、内存、硬盘、网卡等硬件，完成自检（POST），然后按启动顺序把控制权交给操作系统或引导程序。

### 常用厂商进入Bios的快捷键

| :--- | :--- | :--- |
| **Dell** | **F2** | PowerEdge系列的标准按键，在开机出现Dell Logo时按下。 |
| **HPE** | **F9**（或F10） | F9进入UEFI System Utilities（内含BIOS/RBSU配置）；部分旧资料或特定功能（如Intelligent Provisioning）可能指向F10，以屏幕提示为准。 |

### Bios的工作流程

#### 总览：BIOS 工作流程的时间线

BIOS/UEFI 的工作流程，本质上是服务器从**按下电源键**到**操作系统接管**之间的一系列有序动作。整个过程可以划分为五个阶段，

**上电复位 → POST 自检 → 硬件初始化与资源分配 → 引导设备选择与加载 → 交接操作系统**


#### 阶段一：上电复位与固件入口

电源按下后，电源模块（PSU）完成上电时序，向主板输出稳定的各路电压。CPU 收到复位信号后，从**固定的物理地址**（传统 x86 为 `0xFFFFFFF0`）开始取第一条指令。这个地址被映射到主板上的 **BIOS/UEFI 固件芯片**（SPI Flash），而不是内存或硬盘。

CPU 此时运行在**实模式**（Legacy）或固件的早期初始化环境（UEFI），内存尚未初始化，能用的只有极小的缓存和固件芯片本身。固件的第一段代码（Boot Block）开始执行，负责最基础的 CPU 和芯片组初始化，为后续 POST 做准备。

**运维关注点**：如果服务器按电源键后**风扇不转、指示灯不亮**，问题通常在供电或主板，而非 BIOS 流程本身；如果**风扇转但无任何显示和蜂鸣**，可能是固件芯片损坏或 Boot Block 异常。


#### 阶段二：POST 上电自检

这是 BIOS 工作流程中最核心、也最容易出问题的阶段。POST（Power-On Self-Test）按顺序检测和初始化关键硬件，确认系统具备继续启动的基本条件。

**典型检测顺序**：

1. **CPU 自检**：确认 CPU 存在、型号可识别、核心电压正常、缓存可用。
2. **内存初始化与训练**：检测内存条是否安装、SPD 信息是否可读，执行**内存训练（Memory Training）** 以确定稳定的时序和电压。这是服务器 POST 中**耗时最长**的环节之一，大容量内存配置下可能持续数分钟。
3. **芯片组与总线初始化**：初始化 PCIe 根复合体、DMI/UPI 链路、USB 控制器、SATA/SAS 控制器等。
4. **关键外设检测**：枚举 PCIe 设备（RAID 卡、网卡、GPU），读取其 Option ROM 或 UEFI 驱动；检测键盘、显示输出等基本输入输出设备。
5. **电源与散热检查**：确认 PSU 状态、风扇转速、温度传感器读数在可接受范围。

**失败时的表现**：POST 发现致命错误时会**中止启动**，并通过蜂鸣码、前面板诊断代码、屏幕错误信息或 BMC 的 SEL 日志报警。常见如内存未插好（蜂鸣码指向内存）、CPU 未安装、PCIe 设备异常等。

**运维关注点**：**“卡自检”** 是 IDC 最常见故障现象之一。第一反应应是通过 BMC 查看 SEL 日志和远程 KVM 画面，确认卡在哪个阶段（内存训练、PCIe 枚举还是外设检测），再决定是重新插拔内存、更换部件还是重置 BIOS 配置。


#### 阶段三：硬件初始化与资源分配

POST 确认硬件可用后，BIOS 进入更深层的初始化和资源分配阶段，为操作系统准备好一个“干净、可用的硬件环境”。

**主要工作**：

- **内存映射建立**：将物理内存、PCIe 设备 BAR 空间、固件保留区域等统一编入系统地址映射，避免冲突。
- **中断与 DMA 资源分配**：为 PCIe 设备分配中断号、DMA 通道等资源。
- **存储控制器初始化**：RAID 卡固件加载、硬盘识别、启动盘枚举。
- **电源管理与风扇策略生效**：按 BIOS 设置应用节能策略、风扇曲线。
- **安全启动准备**（UEFI 模式）：加载平台密钥（PK）、密钥交换密钥（KEK）、签名数据库（db），为后续验证引导程序签名做准备。

**运维关注点**：这一阶段的行为受 **BIOS 设置**直接影响。虚拟化选项（VT-d、SR-IOV）、启动模式（UEFI/Legacy）、RAID 配置、安全启动开关等，都在这里生效。**更换主板或升级固件后，必须按基线恢复这些配置**，否则可能出现“硬件正常但系统起不来”或“性能不符合预期”的问题。


#### 阶段四：引导设备选择与引导加载

硬件环境就绪后，BIOS 按**启动顺序（Boot Order）** 依次尝试从候选设备加载引导程序。这是 Legacy 和 UEFI 差异最明显的阶段。

**Legacy 模式的引导方式**：

BIOS 读取启动设备**第一个扇区（MBR，512 字节）** 中的引导代码，校验末尾的 `0x55AA` 签名。若有效，将控制权交给这段代码，由它（如 GRUB 的 stage1）继续加载后续引导阶段。Legacy 模式依赖**中断调用**（INT 13h 等）读取磁盘，受 MBR 分区表和 2TB 容量限制。

**UEFI 模式的引导方式**：

UEFI 固件读取 **NVRAM 中的启动项变量**（`Boot####`），按 `BootOrder` 顺序查找每个启动项对应的**设备路径**，定位该设备 **ESP 分区（EFI System Partition）** 中的 `.efi` 引导文件（如 `\EFI\BOOT\BOOTX64.EFI` 或 `\EFI\redhat\grubx64.efi`）。若启用了 **Secure Boot**，固件会验证该 `.efi` 文件的**数字签名**，签名无效则拒绝加载。

**PXE 网络引导**：若启动顺序中排到网络设备，BIOS/UEFI 会通过网卡的 PXE Option ROM 或 UEFI 网络栈发起 DHCP 请求，获取引导文件位置后通过 TFTP 下载并执行。UEFI 下的 PXE 需要 DHCP 服务器能识别 `option 67` 中的 `.efi` 文件名，与 Legacy 的 `pxelinux.0` 不同。

**失败时的表现**：若所有启动设备均未找到有效引导程序，屏幕会提示“No bootable device”或类似信息，BIOS 可能进入设置界面或暂停等待。

**运维关注点**：装系统、PXE 批量部署、救援时，**启动顺序和启动模式必须匹配**。Legacy 装的系统切到 UEFI 模式后找不到引导项，反之亦然。Secure Boot 开启时，未签名的第三方引导程序会被拦截，需确认 OS 和驱动是否支持。


#### 阶段五：交接操作系统与固件运行时服务

引导程序（boot loader）被加载后，BIOS 的“引导”职责基本完成，但固件并未完全退出。

**Legacy 模式**：引导程序接管后，BIOS 通过中断服务（INT 10h 显示、INT 13h 磁盘、INT 15h 系统服务等）继续为实模式下的引导程序提供基础服务，直到 OS 内核切换到保护模式并建立自己的驱动体系。

**UEFI 模式**：引导程序通过 `ExitBootServices()` 通知固件“不再需要启动服务”，固件释放大部分资源。但 **UEFI Runtime Services**（运行时服务）仍然保留，供操作系统在运行期间调用，如读取/写入 NVRAM 变量、获取时间、触发固件更新等。操作系统通过 `efivarfs`（Linux）或 UEFI 运行时接口访问这些服务。

**运维关注点**：UEFI 运行时服务的异常可能导致 OS 启动后出现与固件相关的问题（如 `efibootmgr` 无法修改启动项、NVRAM 变量写入失败）。此外，**固件更新（BIOS/BMC）** 通常通过 OS 内的工具（如 `fwupdmgr`、厂商工具）调用 UEFI 胶囊更新机制完成，更新在下次重启时由固件执行。


#### 流程总结与排障映射

| 阶段 | 核心动作 | 卡住时的典型表现 | 首选排查手段 |
|---|---|---|---|
| **上电复位** | CPU 取指、固件入口 | 风扇不转、无灯 | 查供电、PSU、主板 |
| **POST 自检** | CPU/内存/PCIe/外设检测 | 卡 Logo、蜂鸣码、诊断代码 | BMC SEL、远程 KVM、最小化硬件 |
| **硬件初始化** | 资源分配、RAID/安全启动准备 | 硬件识别异常、RAID 丢失 | 核对 BIOS 配置基线、RAID 卡状态 |
| **引导加载** | 按 Boot Order 加载 boot loader | “No bootable device”、Secure Boot 拦截 | 核对启动模式、启动顺序、ESP 分区、签名 |
| **交接 OS** | ExitBootServices、运行时服务 | OS 启动后固件相关异常 | 查 `efibootmgr`、NVRAM、固件版本 |

**一句话总结：BIOS 的工作流程是“上电取指 → POST 自检 → 硬件初始化与资源分配 → 按启动顺序加载引导程序 → 交接操作系统并保留运行时服务”；IDC 运维中判断服务器启动故障，本质上就是判断它卡在这条时间线的哪一段，再用 BMC SEL、远程 KVM 和最小化硬件测试逐段定位。**

### Bios的核心作用

BIOS/UEFI 固件在服务器启动和运行中承担四项不可替代的核心作用，按执行顺序和重要性排列如下。

#### 核心作用一：上电自检（POST）

这是 BIOS 最先执行、也是运维中最常打交道的功能。服务器加电后，BIOS 立即对 CPU、内存、PCIe 设备、存储控制器、电源等关键硬件进行检测和初始化，确认硬件处于可用状态。若发现致命故障（如内存未插、CPU 异常），POST 会中止启动并通过蜂鸣码、屏幕错误信息或诊断代码报警，避免系统在硬件不稳定的状态下继续运行。**没有 POST，服务器无法确认自身硬件是否健康，也就无法安全地进入下一步。**

#### 核心作用二：硬件初始化与资源分配

POST 通过后，BIOS 负责对硬件进行更深层的初始化和资源分配，包括：

- 配置内存参数（频率、时序、ECC 模式）；
- 枚举和分配 PCIe 设备的总线号、内存映射和中断资源；
- 初始化板载网卡、RAID 卡、USB 控制器等；
- 设置电源管理策略和风扇控制策略。

这一步决定了操作系统能看到哪些硬件、以什么方式访问它们。**BIOS 是硬件与操作系统之间的“翻译层”，没有它完成初始化，OS 无法直接驱动裸硬件。**

#### 核心作用三：引导加载（Boot）

硬件初始化完成后，BIOS 按设定的**启动顺序**（Boot Order）依次尝试从硬盘、PXE 网络、光驱、U 盘等设备加载引导程序（boot loader），找到后将控制权交给它，由引导程序进一步加载操作系统内核。启动模式（Legacy BIOS 或 UEFI）、安全启动（Secure Boot）开关、PXE 是否启用等，都在这一步起作用。**这是 BIOS 最直观的“启动”功能，也是装系统、PXE 批量部署、救援时最常调整的部分。**

#### 核心作用四：提供配置接口与基础管理

BIOS/UEFI 设置界面是运维人员配置底层硬件行为的入口，包括：

- 启动模式与启动顺序；
- 虚拟化选项（VT-d、SR-IOV、IOMMU）；
- 超线程与节能策略；
- RAID 配置入口（部分机型）；
- 安全启动与固件密码；
- 硬件监控阈值与告警策略。

这些设置直接影响性能、兼容性和安全性，**是 IDC 运维中变更前必须记录、更换主板后必须恢复的关键配置基线。**

#### 总结

**BIOS 的四个核心作用是：POST 自检确认硬件可用 → 初始化硬件并分配资源 → 按启动顺序引导操作系统 → 提供底层配置接口。前两步保证“机器能正常起来”，第三步保证“系统能被找到并加载”，第四步保证“运维能按需调整硬件行为”。** 四者缺一不可，其中 POST 和硬件初始化是基础，引导是结果，配置接口是运维控制手段。


### Bios的两种启动模式

BIOS的两种启动模式，**UEFI**和**Legacy**（也称传统BIOS或CSM），是服务器引导操作系统的两种不同底层机制。它们的核心区别在于**引导方式、分区表格式和功能特性**，这直接决定了服务器的启动速度、硬盘容量支持、安全性和兼容性。

#### 💻 核心区别：一张表看懂

下表汇总了两者在关键技术特性上的主要差异。

| 对比维度 | **UEFI 启动模式** | **Legacy BIOS 启动模式** |
| :--- | :--- | :--- |
| **硬盘分区表** | **GPT** (GUID Partition Table) | **MBR** (Master Boot Record) |
| **最大硬盘容量** | **大于 2TB**，理论上无上限 | **最大 2TB**，超出部分无法识别 |
| **主分区数量** | 最多 **128个** | 最多 **4个** |
| **启动速度** | **更快**，支持并行初始化硬件 | 相对较慢，硬件需逐一串行自检 |
| **安全启动** | **支持 Secure Boot**，可验证引导程序签名，防御Bootkit | **不支持** |
| **引导文件** | 读取ESP分区中的 **`.efi`** 文件 | 读取磁盘第一个扇区的**引导代码** |
| **固件运行模式** | 32位或64位原生模式 | 16位实模式 |
| **界面与诊断** | 图形化界面，诊断工具更丰富 | 通常是文本界面，诊断能力有限 |

#### 🚀 UEFI：现代服务器的默认标准

UEFI（Unified Extensible Firmware Interface，统一可扩展固件接口）是为取代老旧BIOS而设计的现代固件接口，现已成为绝大多数新服务器的默认模式。

**核心优势**
- **突破容量与分区限制**：原生配合**GPT分区表**，彻底解决2TB硬盘容量瓶颈，并支持创建海量分区，这是运维中最直接的收益。
- **启动速度显著提升**：以32/64位模式运行，能**并行初始化**多个硬件，并直接扫描ESP分区中的`.efi`文件，跳过Legacy的扇区跳转流程，尤其在NVMe SSD上效果明显。
- **安全性**：**Secure Boot（安全启动）** 是UEFI的标志性功能，它通过验证引导加载程序的数字签名，能有效阻止未签名或恶意的引导程序运行，防御Bootkit类攻击。
- **强大的诊断与管理**：提供图形化界面，并常集成硬件诊断、固件日志查看等工具，比Legacy的纯文本界面更利于排障。

#### 🕰️ Legacy BIOS：为兼容而生的传统模式

Legacy BIOS是沿用数十年的传统启动方式，其设计基于16位实模式，核心考量是**极致的兼容性**，而非性能和现代特性。

**适用场景与局限**
- **主要价值在于兼容**：当需要安装**不支持UEFI的旧版操作系统**（如Windows Server 2008 R2及更早版本），或使用**必须依赖传统Option ROM的老旧PCIe扩展卡**（如某些HBA卡）时，Legacy模式是必要的选择。
- **固有的技术局限**：受MBR分区表限制，**无法使用超过2TB的磁盘空间**；**没有Secure Boot**；启动过程依赖中断调用，效率较低；界面通常是蓝底文本模式，交互和诊断能力有限。

#### 🧩 补充概念：CSM（兼容性支持模块）

**CSM**是UEFI固件中的一个**兼容层**。开启CSM后，UEFI固件可以模拟Legacy BIOS的行为，来引导那些没有UEFI驱动的老设备或旧系统。但需要注意，**开启CSM通常会禁用Secure Boot**，并且启动速度会回落到接近Legacy的水平，其分区表也受限于MBR策略。因此，CSM是一种过渡方案，而非独立的启动模式。

#### 🛠️ IDC运维中的关键实践

在服务器运维中，启动模式的选择和切换是高风险操作，需遵循以下原则：

**模式选择原则**
- **默认选UEFI**：对于所有支持的新操作系统（现代Windows Server、主流Linux发行版）和新硬件，**应优先选择UEFI模式**。这是发挥服务器全部性能和安全特性的基础。
- **按需退Legacy**：仅在明确需要兼容老旧OS或特定扩展卡时，才选用Legacy模式。

**切换模式的核心注意事项**
**启动模式与磁盘分区表是强绑定的**。UEFI需要GPT，Legacy需要MBR。**在已安装操作系统的服务器上直接切换启动模式，会导致系统无法引导**，因为固件按照新模式找不到对应的引导记录。

如果确需切换，必须：
1.  **备份数据**。
2.  在Legacy转UEFI时，通常需要**将磁盘从MBR转换为GPT**（可使用`mbr2gpt`等工具，但前提是磁盘布局满足转换条件），或**重装操作系统**并选择UEFI引导。
3.  在UEFI转Legacy时，则需要将磁盘从GPT转换为MBR，或重装系统。

**运维检查点**
- **确认当前模式**：在Windows系统内，可通过`msinfo32`的“BIOS模式”项快速查看；在Linux内，可通过检查是否存在`/sys/firmware/efi`目录来判断。
- **PXE批量部署**：需确保DHCP/TFTP环境能同时或按需支持UEFI和Legacy两种客户端的引导请求，这在混合环境中尤其重要。
- **大容量存储**：当服务器配置超过2TB的RAID卷或单盘时，必须使用UEFI+GPT模式，否则多余容量在Legacy模式下将无法被系统识别和使用。

**总结来说，UEFI是面向现代硬件和操作系统的标准，提供了速度、容量和安全性的全面升级；而Legacy模式的核心价值在于对旧有生态的兼容。在运维决策中，应以UEFI为默认选择，仅在明确的兼容性需求下才使用Legacy，并始终警惕切换启动模式所带来的系统引导风险。**


## 总线

**总线（Bus）** 是计算机各部件之间传输信息的**公共通信通道**。它是一组物理导线或信号线，按约定协议在 CPU、内存、芯片组、外设之间传递**数据、地址和控制信号**。总线的核心价值在于**用一套共享的通信规则替代点对点直连**，从而降低布线复杂度、支持设备扩展、统一通信标准。

### 总线的作用和分类

#### 总线的作用

- **连接部件**：把 CPU、内存、PCIe 设备、存储控制器、USB 设备等连接成一个可协同工作的系统。
- **传输数据**：在源部件和目的部件之间搬运数据。
- **传递地址**：告诉系统“这次访问的是哪个内存地址或哪个设备”。
- **传递控制信号**：如读/写命令、中断、时钟、复位、总线仲裁等。
- **支持扩展**：通过标准化总线接口，设备可以按规范接入，而不需要为每个设备单独设计连线。
- **仲裁与同步**：多个设备争用总线时，由仲裁机制决定谁先使用；通过时钟或握手协议保证双方同步。

#### 按功能分类：数据总线、地址总线、控制总线

这是最经典的分类方式，按总线传输的信号类型划分。

| 类型 | 传输内容 | 方向 | 作用 |
| :--- | :--- | :--- | :--- |
| **数据总线** | 实际数据 | 双向 | 在 CPU、内存、外设之间搬运数据；**宽度**决定一次能传多少位，如 32 位、64 位 |
| **地址总线** | 地址信息 | 单向（CPU 发出） | 指定要访问的内存地址或设备地址；**宽度**决定可寻址空间大小，如 32 位地址总线对应 4GB 寻址空间 |
| **控制总线** | 控制信号 | 双向/单向混合 | 传递读/写命令、中断请求、时钟、复位、总线请求与应答等 |

三者常合称**系统总线**，是 CPU 与内存、I/O 之间通信的基础。

#### 按层次和位置分类

现代计算机采用**分层总线结构**，不同层次的总线承担不同范围的连接任务。

- **片内总线（On-chip Bus）** ：芯片内部各模块之间的连接，如 CPU 内部核与缓存、SoC 内部 CPU 与 GPU/NPU/外设控制器之间的总线。常见如 **AMBA AHB/AXI/ACE**（ARM 生态）、**CoreConnect**（PowerPC 生态）。
- **系统总线（System Bus）** ：连接 CPU、内存控制器、芯片组等主要部件，如传统前端总线（FSB）、Intel 的 **QPI/UPI**、AMD 的 **Infinity Fabric**。
- **I/O 总线/外设总线**：连接主板与外部设备或扩展卡，如 **PCIe**、**USB**、**SATA**、**SAS**、**I2C**、**SPI**、**UART**。
- **存储总线**：连接存储设备，如 SATA、SAS、NVMe（走 PCIe）、DDR 内存总线。
- **现场总线/工业总线**：工业控制和嵌入式场景，如 **CAN**、**Modbus**、**PROFIBUS**、**PROFINET**。

#### 按传输方式分类：串行总线与并行总线

| 类型 | 特点 | 典型例子 |
| :--- | :--- | :--- |
| **并行总线** | 多位数据同时传输，线宽大，短距离内带宽高，但存在**信号偏斜**和**串扰**，难以高频长距离传输 | 传统 PCI、IDE、早期内存总线、CPU 前端总线 |
| **串行总线** | 数据按位顺序传输，线少、抗干扰好、可高频、易长距离传输，可通过多通道聚合提升带宽 | **PCIe**、**USB**、**SATA**、**SAS**、**NVMe**、**以太网**、**I2C**、**SPI** |

现代高速总线基本以**串行**为主，PCIe 就是典型代表：用串行差分信号替代并行 PCI，通过多 Lane 聚合实现高带宽。

#### 按使用范围和协议分类

- **专用总线**：为特定部件设计，如内存总线（DDR）、CPU 互连总线（UPI、Infinity Fabric）。
- **标准扩展总线**：按公开标准设计，支持第三方设备接入，如 PCIe、USB。
- **现场总线**：面向工业现场设备，强调实时性、可靠性和抗干扰，如 CAN、PROFIBUS、PROFINET。

#### IDC 运维中的常见总线

- **PCIe**：服务器扩展卡（网卡、RAID 卡、GPU、NVMe SSD）的主力总线，关注 Lane 数、代际（Gen3/Gen4/Gen5）、带宽和插槽分配。
- **DDR 内存总线**：CPU 与内存之间的专用高速总线，关注代际（DDR4/DDR5）、频率、通道数和 ECC。
- **UPI/Infinity Fabric**：多路 CPU 之间的互连总线，影响 NUMA 架构和跨 CPU 访问延迟。
- **SATA/SAS**：硬盘和 SSD 的存储总线，关注速率、双端口和扩展能力。
- **USB**：主要用于管理口、外设和部分 BMC 连接。
- **I2C/SPI**：板级管理总线，常用于 BMC 读取传感器、访问 FRU、连接光模块管理接口等。
- **以太网**：严格说是网络标准，但在 IDC 中也是服务器与交换机之间的“外部总线”，关注速率、双工、光模块和链路聚合。

#### 一句话总结

**总线是计算机各部件之间共享的通信通道，负责传数据、传地址、传控制信号；按功能分数据/地址/控制总线，按层次分片内/系统/I/O/存储/现场总线，按传输方式分串行/并行，现代高速总线以串行为主；IDC 运维中最常打交道的是 PCIe、DDR、UPI/Infinity Fabric、SATA/SAS、USB 和 I2C/SPI。**
